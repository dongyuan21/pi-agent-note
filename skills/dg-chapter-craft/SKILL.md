# dg-chapter-craft · 技术章节写作方法论

> 本 skill 蒸馏自本仓库「源码精读 / 实战上手」双轨教程的实际写法与 `_chapter-design` 设计文档。
> 目标：让 AI（或人类编辑）按同一套工艺写章、改章、审章——不是贴代码加注释，而是让读者带走可迁移理解。

## When to Use

- 新开一章 / 重写一章 / 写章节设计文档
- 审稿：判断一章是否「稳」（概念清楚、机制闭环、取舍讲透、能带走方法）
- 把散乱源码笔记改造成可发布章节
- 为配图、Before/After、源码索引规划内容锚点

**不要**用本 skill 去查 Pi API 细节或写可运行 SDK 示例——那是 SDK 开发 skill 的事。本 skill 只管**叙事与认知工程**。

---

## 一、总原则（一句话）

每一章都必须让读者在离开时同时带走三样东西：

1. **概念**——这东西是什么  
2. **机制**——源码/系统怎么做到的  
3. **判断力**——为什么这样取舍，以及自己项目里怎么复用  

对应固定三问：**是什么 / 怎么做 / 为什么这样做**。缺一问，章就不完整。

---

## 二、强制工作流

写章或改章时，**禁止直接开写正文**。按顺序产出：

```
① 章节设计文档  →  ② 自检清单全绿  →  ③ 正文  →  ④ 配图/索引/悬念收口
```

设计文档模板见 [references/chapter-design-template.md](references/chapter-design-template.md)。  
自检清单见 [references/self-check.md](references/self-check.md)。

若用户只要「小修小补」（typo、链接、措辞），可跳过设计文档；一旦动结构、增删主线、改认知节奏，必须回到 ①。

## 三、四大工艺（本 skill 的核心）

### 3.1 三问推进：是什么 → 怎么做 → 为什么

| 层 | 读者得到什么 | 常见载体 | 反例（禁止） |
|----|-------------|---------|-------------|
| **是什么** | 可复述的概念边界 | 一句话定义、对照表、ASCII/配图全景 | 上来贴 80 行源码 |
| **怎么做** | 能顺着调用链走通 | 关键路径 + 精简代码 + 步骤管道 | 只罗列文件名 |
| **为什么** | 设计张力与取舍 | 反例、对比表、失败模式、成本分析 | 「业界最佳实践」空话 |

写法约束：

- 一节里可以三问交织，但**读者必须能指出本节主答哪一问**
- 「怎么做」必须落到**可核对的源码位置**（包路径 + 符号；行号可写约数并注明版本）
- 「为什么」必须点出**若选另一方案会坏在哪**，否则不算取舍

### 3.2 建 → 破 → 立（认知循环）

每个主线知识点至少走一轮：

| 阶段 | 作用 | 读者感受（设计文档里要写出来） |
|------|------|-------------------------------|
| **建** | 先给可用心智模型 / 表面正确的图景 | 「原来如此 / 挺简单」 |
| **破** | 用真实矛盾、边界、时机问题掀翻它 | 「不对啊，那这个怎么办？」 |
| **立** | 给出真正机制，并回扣开场需求 | 「妙在这里——约束被接住了」 |

约束：

- 一章通常 **2～3 个**循环；超过 4 个会疲劳
- 「破」必须是**读者真会问的**，不是作者自嗨的术语游戏
- 「立」必须同时回答机制 **和** 工程动机
- 禁止只有「建」没有「破」的平铺说明书

### 3.3 链路闭环

凡讲事件、管道、钩子、存储、压缩、扩展……**禁止只报名字**。每条关键链路必须写全：

```
触发端 → 中转（谁 emit / 谁调用）→ 消费端 → 最终结果（用户/模型/状态可见什么）
```

在设计文档里维护「链路闭环清单」表；正文至少完整走通 **1 条主链路**（可再附 1～2 条变体）。

断链信号（出现即不合格）：

- 只写「这里会发 `tool_call` 事件」却不写谁处理、返回值如何改变后续
- 只写「然后压缩」却不写摘要写回何处、下一轮如何读到
- 配图节点无法映射到正文某一步

### 3.4 可迁移方法论

每章收尾前必须有一节（名可叫「方法论提炼 / 设计精华 / 可以带走的方法」），条目满足：

| 要求 | 说明 |
|------|------|
| **有名字** | 可称呼、可检索（如「错误即消息」「依赖漏斗」） |
| **有来源** | 明确来自本章哪段机制 |
| **有复用指引** | 读者在自己项目里何时用、怎么验 |
| **可脱离 Pi 叙述** | 删掉 Pi 专有名词后，方法仍成立 |

推荐每条用迷你三问再收一遍：**是什么 / 怎么做 / 怎么验证**（见第 2 章「三个可以带走的方法」写法）。

数量：通常 **3～5 条**；宁少勿水。

## 四、章节骨架（正文默认顺序）

可按题材微调，但默认按此装配：

1. **开场钩子**：真实需求 / 上一章悬念 / 反直觉问题（制造「我需要读这章」）
2. **是什么**：边界、一张全景图、关键术语只引入本章要用的
3. **怎么做（主链路）**：跟一条完整路径走，边走边揭机制
4. **建破立循环**：把最精妙/最易懵的点放这里
5. **数据展示**：Before/After、字段级变化、状态机或树的生长过程
6. **为什么 / 取舍**：对比表、失败模式、不做的事
7. **方法论提炼**
8. **收尾回扣开场** + **下一站悬念**（只抛问题，不剧透答案）
9. **本章关键源码索引**（路径列表；与正文引用一致）

实战篇差异：用「场景任务 → 改哪一层 → 可运行代码 → 验收现象」替换部分源码深潜，但三问、闭环、方法论**不减**。

## 五、辅助工艺

### 5.1 概念空白清单

设计阶段列出：读者已知 / 未知 / 模糊。对每个空白规定：

- 引入策略（类比 / 对比 / 一句话定义 / 备菜后用）
- 引入位置（第几节）
- 类比或解释（类比必须标明**失效边界**）

### 5.2 叙事起点类型（选一种做主起点）

| 类型 | 适用 |
|------|------|
| 设计问题（「为什么要搞这个？」） | 架构、扩展、分层 |
| 运行时追踪（「一次调用发生了什么？」） | Loop、工具管道、上下文链路 |
| 存储/结构问题（「数据长什么样？」） | 消息、会话树 |
| 故障/限制（「窗口满了怎么办？」） | 压缩、截断、限流 |

禁止起点：「本章介绍 XXX 模块的 API」。

### 5.3 配图

- 图服务于**一个**认知目标（结构 / 时序 / 状态变化）
- 必须有「配图说明」：读者该从这张图读出什么
- 图内节点应能锚到正文步骤或代码块（Web 版可做点击联动）
- 无图时至少给 ASCII 全景，避免纯散文堆概念

### 5.4 源码引用规范

- 包内路径优先：`packages/.../file.ts` 的 `symbolName`
- 证明观点时写清：**这段代码证明了设计文档里的哪一条**
- 行号随版本漂移：写「约 Lxxx」或「符号定位」，并在章首/章末声明对照的 Pi 版本基线
- **当前工程约定的 Pi 讨论基线：最新稳定版**（查证方式：`npm view @earendil-works/pi-coding-agent version` 与 GitHub `earendil-works/pi` Releases；写作时记下具体版本号）

### 5.5 收束句式

- 收尾先**回到开场问题**，用一段「现在你有完整答案」收口
- 「下一站」只留悬念与接口词（如 Session Tree），把答案留给下章
- 不要在章末突然引入未铺垫的新体系

## 六、审稿时怎么用本 skill

按 [references/self-check.md](references/self-check.md) 逐项打勾。优先堵这四类漏洞：

1. 只有 API 罗列，没有「为什么」  
2. 有「破」点但没有立住（悬空术语）  
3. 事件/管道断链  
4. 方法论无法脱离本章场景复述  

输出审稿意见时：先给**一句话总评**，再按「必须改 / 建议改 / 可保留」列点；不要只夸文笔。

## 七、产出物清单

| 产出 | 何时必须有 |
|------|-----------|
| `_chapter-design/第N章-….md` | 新章或结构性改写 |
| 正文 `.md`（及 Web `.mdx` 若已入站点） | 发布 |
| 配图 `assets/`（svg/html） | 有结构/时序需要时 |
| 源码索引段 | 源码精读每章文末 |
| 方法论节 | 每章 |

Python 对照版：保留非代码叙述，只改写代码块；规则见 `pi-agent/pi_source_dive/python/README.md`。设计文档与方法论对 TS/Python **同一套**，不因语言分叉。

---

## 八、快速指令（给使用本 skill 的 Agent）

用户说「按 dg-chapter-craft 写第 N 章」时：

1. 读相关前章结尾悬念 + 本主题源码（按当前 Pi 稳定版）  
2. 先交设计文档（含概念空白、建破立、链路闭环、数据展示、篇幅规划）  
3. 等设计文档自检通过（或用户确认）后再写正文  
4. 正文写完再跑自检，修断链与方法论空洞  
5. 最后补源码索引与下一站悬念  

用户说「审这一章」时：只输出自检结果与修改清单，除非明确要求直接改稿。
