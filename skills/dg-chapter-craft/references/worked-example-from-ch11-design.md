# 范例：如何把「写法」填进设计文档

> 素材来源：本仓库已有的 `第11章-扩展系统-设计文档.md`（**仅作工艺范例**，不代表必须立刻写该章正文）。  
> 用途：对照模板，看「一句话认知变化 / 建破立 / 链路闭环 / 方法论」怎样写才算合格。

---

## 1. 本章一句话（合格 vs 不合格）

**不合格（主题列表）**  
「这章讲了 28 个事件、注册机制、两阶段绑定。」

**合格（认知变化）**  
「扩展系统不是魔法注入，而是 Pi 在工作流关键点 emit 事件——用『约定（事件名 + 返回值协议）』换『灵活（不改源码）』。」

判别法：删掉专有名词后，读者是否仍感到「我以前想错了」。

---

## 2. 叙事线索（需求串机制）

范例主线：团队要禁止 `rm -rf` → 改源码成本高 → 用扩展 → 目录加载 → 工厂函数 → `tool_call` 返回 block → Loop 跳过执行 → 用户看到拒绝。

要点：机制讲解都挂在这条需求的旅程上，而不是按 `loader → runner → types` 的实现目录平铺。

---

## 3. 建 → 破 → 立（摘录结构）

| 循环 | 建 | 破 | 立 |
|------|----|----|----|
| 1 | 六个真实场景证明扩展很强 | Pi 预先不知道你的需求，怎能扩展？ | 事件总线：关键点 emit，扩展用返回值协议介入 |
| 2 | 工厂函数里 `pi.on` 看起来很简单 | 工厂函数执行时 Agent 还不存在 | throwing stubs + `bindCore` 两阶段绑定 |
| 3 | 扩展能力很大 | 扩展抛错/作恶怎么办？ | 错误隔离 + 三层 API 门面 |

注意：每个阶段都写了「读者感受」——这是设计文档约束作者不要自嗨。

---

## 4. 链路闭环（一条就够示范）

| 字段 | 内容 |
|------|------|
| 触发端 | 用户输入导致 bash 工具参数含 `rm -rf` |
| 中转 | Loop 执行前 `emit("tool_call")` |
| 消费端 | 扩展返回 `{ block: true, reason }` |
| 最终结果 | 跳过执行，错误消息回给模型，模型可改道 |

断链写法反例：「系统支持 `tool_call` 事件。」——没有消费与结果。

---

## 5. 方法论条目形状

范例条目：

- **名称**：事件总线暴露关键点  
- **来源**：工作流 8 个关键点 emit  
- **复用**：设计插件系统时先标关键节点，统一事件，而不是为每个点写死 hook 函数  
- **验证**：新增第三方行为时是否无需改核心、只加订阅者

可脱离 Pi 复述：任意「核心稳定、外围演化」的运行时都能用。

---

## 6. 从范例可复用的检查句

写完任一章设计文档后，大声问：

1. 一句话是「目录」还是「认知变化」？  
2. 主线是「读者旅程」还是「源码目录漫步」？  
3. 每个精妙点是否有破？  
4. 主链路是否追到用户/模型可见结果？  
5. 方法论能不能拿到别的 Agent 框架上讲？
